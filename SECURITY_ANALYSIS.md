# Анализ безопасности API Calculator

## 1. Цель анализа

Цель этапа — встроить в CI-пайплайн автоматические средства анализа безопасности, выполнить проверки проекта и проанализировать найденные проблемы.

В проекте используются следующие инструменты:

- Semgrep — статический анализ исходного кода и конфигурации;
- Trivy — проверка Docker-образа и зависимостей;
- Syft — создание SBOM;
- Grype — поиск уязвимостей в компонентах из SBOM;
- Gitleaks — поиск секретов в Git-репозитории;
- Checkov — анализ Dockerfile и CI-конфигурации.

## 2. Архитектура CI после доработки

Первоначально pipeline выполнялся на GitHub-hosted Ubuntu runner.

После замечания преподавателя был настроен Windows self-hosted runner.

Текущая схема:

```text
push в ветку main
→ GitHub Actions
→ Windows self-hosted runner
→ Docker Desktop
→ docker build по Dockerfile
→ запуск security-инструментов через Docker
→ анализ результатов
```

Основной job использует:

```yaml
runs-on: [self-hosted, Windows, X64]
```

Self-hosted runner успешно подключён к GitHub и принимает задания.

Тестовый job выполнился успешно, после чего основной job:

```text
Build and Security Scan
```

также завершился со статусом:

```text
Succeeded
```

Таким образом, основной CI-пайплайн больше не зависит от `ubuntu-latest`.

## 3. Сборка приложения

Сборка приложения выполняется непосредственно через:

```text
docker build
```

Вся логика сборки описана в Dockerfile.

Dockerfile:

- использует базовый образ `python:3.13-slim`;
- получает `APP_VERSION`;
- задаёт рабочую директорию `/app`;
- копирует `requirements.txt`;
- устанавливает Python-зависимости;
- копирует `main.py`;
- запускает Uvicorn на порту 8000.

Таким образом, pipeline не повторяет отдельно установку Python и зависимостей, а использует Dockerfile как единое описание сборки приложения.

## 4. Semgrep

Semgrep выполняет статический анализ исходного кода и файлов конфигурации.

В зафиксированном полном запуске были получены результаты:

- проверено файлов: 8;
- выполнено правил: 329;
- обнаружено замечаний: 11;
- blocking findings: 11.

### Основные замечания

10 замечаний были связаны с использованием GitHub Actions по изменяемым тегам версий, например:

```yaml
uses: actions/checkout@v6
uses: aquasecurity/trivy-action@v0.36.0
uses: anchore/sbom-action@v0
uses: anchore/scan-action@v7
uses: gitleaks/gitleaks-action@v3
uses: bridgecrewio/checkov-action@v12
```

Такой тег может быть перенаправлен на другой commit.

Более безопасный вариант — использовать полный commit SHA.

Пример:

```yaml
uses: actions/checkout@<FULL_COMMIT_SHA>
```

Ещё одно замечание связано с отсутствием инструкции `USER` в Dockerfile.

Без отдельного пользователя процесс внутри контейнера может выполняться от root.

### Рекомендация

Создать непривилегированного пользователя:

```dockerfile
RUN useradd -m -u 10001 appuser
USER appuser
```

## 6. Syft

Syft используется для формирования SBOM Docker-образа.

SBOM — это перечень программных компонентов:

- библиотек;
- системных пакетов;
- зависимостей;
- их версий.

В зафиксированном запуске Syft успешно сформировал SBOM для образа:

```text
calculator-api:1.0.6
```

Формат:

```text
SPDX JSON
```

Полученный SBOM далее используется инструментом Grype.

## 7. Grype

Grype проверяет компоненты из SBOM на известные уязвимости.

В зафиксированном запуске Grype обнаружил уязвимости в системных пакетах Docker-образа, в том числе уровня HIGH.

Среди затронутых компонентов были:

- `ncurses-bin`;
- `libc-bin`;
- `libc6`;
- `zlib1g`;
- `gcc-14-base`;
- `libgcc-s1`;
- `libstdc++6`;
- `util-linux`;
- `libacl1`.

Для значительной части результатов была указана пометка:

```text

```

Это означает, что для используемой версии пакета в источнике данных исправление не предлагается.

### Почему Trivy и Grype показывают разные результаты

Это не является ошибкой.

Инструменты используют:

- разные базы уязвимостей;
- разные правила сопоставления;
- разные настройки фильтрации.

В Trivy была включена настройка игнорирования части уязвимостей без доступного исправления, а Grype показывал в том числе такие записи с пометкой `won't fix`.

Поэтому совместное использование инструментов даёт более полную картину.

## 9. Checkov

Checkov проверяет Dockerfile и GitHub Actions на небезопасные настройки.

### Dockerfile

Результаты:

- Passed checks: 33;
- Failed checks: 2;
- Skipped checks: 0.

Обнаружены две проблемы.

### Отсутствует HEALTHCHECK

Проверка:

```text
CKV_DOCKER_2
```

В Dockerfile отсутствует инструкция `HEALTHCHECK`.

Это означает, что Docker не имеет встроенной проверки того, отвечает ли приложение внутри работающего контейнера.

Рекомендуется добавить healthcheck для API.

### Отсутствует отдельный пользователь

Проверка:

```text
CKV_DOCKER_3
```

Checkov подтвердил замечание Semgrep: приложение запускается без отдельного непривилегированного пользователя.

Рекомендуется добавить:

```dockerfile
USER appuser
```

### GitHub Actions

В зафиксированном полном запуске:

- Passed checks: 76;
- Failed checks: 0;
- Skipped checks: 0.

По использованному набору правил Checkov не обнаружил проблем конфигурации GitHub Actions.

## 11. Предлагаемые меры

Для повышения безопасности проекта рекомендуется:

1. Использовать конкретные commit SHA для внешних GitHub Actions там, где Actions продолжают использоваться.
2. Добавить непривилегированного пользователя в Dockerfile.
3. Добавить `HEALTHCHECK`.
4. Обновить `msgpack` минимум до `1.2.1`.
5. Обновить `setuptools` минимум до `78.1.1`.
6. Обновить `urllib3` минимум до `2.8.0`.
7. Регулярно обновлять базовый Docker-образ.
8. Повторно проверять системные пакеты после обновления образа.
9. Продолжать создание SBOM через Syft.
10. Продолжать анализ SBOM через Grype.
11. Продолжать поиск секретов через Gitleaks.
12. Продолжать анализ конфигурации через Checkov.
13. Запускать все проверки автоматически при каждом push.
