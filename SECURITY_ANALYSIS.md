# Анализ безопасности API Calculator

## 1. Используемые инструменты

В CI-пайплайн проекта интегрированы шесть средств анализа:

- **Semgrep** — статический анализ исходного кода и файлов конфигурации;
- **Trivy** — анализ Docker-образа, системных пакетов и Python-зависимостей;
- **Syft** — построение SBOM, то есть перечня программных компонентов и их версий внутри Docker-образа;
- **Grype** — поиск известных уязвимостей по компонентам, перечисленным в SBOM;
- **Gitleaks** — поиск секретов, токенов, паролей и ключей в репозитории и истории Git;
- **Checkov** — поиск небезопасных настроек в Dockerfile и CI/CD-конфигурации.

Проверки автоматически запускаются при каждом push в ветку `main`.

## 2. Сборка приложения в CI

Сборка приложения выполняется непосредственно через `docker build`. CI не устанавливает Python и зависимости отдельными шагами.

Вся логика подготовки среды находится в `Dockerfile`:

1. используется базовый образ `python:3.13-slim`;
2. принимается номер версии через `APP_VERSION`;
3. создаётся рабочая директория `/app`;
4. копируется `requirements.txt`;
5. устанавливаются Python-зависимости;
6. копируется `main.py`;
7. задаётся порт 8000 и команда запуска Uvicorn.

Такой подход позволяет проверять именно тот способ сборки, который используется для итогового Docker-образа.

### 3.1 Использование изменяемых тегов GitHub Actions

В workflow использовались ссылки на GitHub Actions по тегам версий, например `@v4`, `@v5` и `@v0.36.0`.

Semgrep определил это как потенциальный риск цепочки поставки, поскольку тег версии может быть изменён владельцем Action. Более строгий вариант — закрепление Action на конкретный commit SHA.

### Предлагаемое улучшение

Использовать полный commit SHA вместо изменяемого тега.

Пример:

```yaml
uses: actions/checkout@<COMMIT_SHA>
```

### 3.2 Запуск Docker-контейнера от root

В Dockerfile отсутствует инструкция `USER`, поэтому процесс внутри контейнера по умолчанию запускается от пользователя root.

Это увеличивает потенциальные последствия компрометации приложения.

### Предлагаемое улучшение

Создать отдельного непривилегированного пользователя и запускать приложение от его имени.

Пример:

```dockerfile
RUN useradd -m -u 10001 appuser
USER appuser
```

## 5. Syft и SBOM

Syft добавлен для формирования SBOM Docker-образа.

SBOM представляет собой перечень программных компонентов, библиотек и их версий. В пайплайне Syft формирует файл `sbom.spdx.json` в формате SPDX JSON.

Этот файл затем передаётся Grype для анализа уязвимостей.

Цепочка анализа выглядит следующим образом:

```text
Docker image -> Syft -> SBOM -> Grype -> список найденных уязвимостей
```

После первого запуска обновлённого workflow необходимо зафиксировать в этом разделе фактический результат Syft: успешность создания SBOM и основные обнаруженные компоненты.

## 6. Результаты Grype

Grype анализирует SBOM, сформированный Syft, и сопоставляет найденные компоненты с базой известных уязвимостей.

В workflow установлен режим `fail-build: false`, поэтому найденные уязвимости отображаются в отчёте, но не останавливают остальные проверки.

**Фактические результаты необходимо добавить после первого запуска обновлённого workflow:**

- количество найденных уязвимостей;
- уровни опасности;
- названия уязвимых компонентов;
- CVE/GHSA;
- установленные и исправленные версии.

## 7. Результаты Gitleaks

Gitleaks проверяет репозиторий и полную историю Git на наличие случайно опубликованных секретов: токенов, паролей, API-ключей и других чувствительных значений.

Для получения полной истории в `actions/checkout` используется `fetch-depth: 0`.

**После запуска необходимо указать фактический результат:** обнаружены ли секреты и, если да, в каких файлах или коммитах.

Если секрет обнаружен, его недостаточно только удалить из текущего файла: секрет необходимо отозвать или заменить, поскольку он мог сохраниться в истории Git.

## 8. Результаты Checkov

Checkov анализирует конфигурацию проекта и ищет небезопасные настройки в Dockerfile и CI/CD-файлах.

В workflow используется `soft_fail: true`, поэтому замечания выводятся в отчёт, но не останавливают остальные проверки.

**После запуска необходимо зафиксировать:**

- количество пройденных проверок;
- количество проваленных проверок;
- идентификаторы замечаний Checkov;
- файлы и строки, к которым относятся замечания;
- предлагаемые способы исправления.

## 9. Итог анализа

На предыдущем этапе Semgrep обнаружил 6 замечаний, а Trivy — две уязвимости уровня HIGH в Python-пакетах `msgpack` и `setuptools`. Уязвимостей уровня CRITICAL обнаружено не было.

После расширения CI-пайплайна проверка безопасности охватывает несколько уровней:

- исходный код и конфигурацию — Semgrep;
- Docker-образ и зависимости — Trivy;
- состав программного обеспечения — Syft;
- уязвимости компонентов из SBOM — Grype;
- секреты в Git — Gitleaks;
- ошибки конфигурации Docker и CI/CD — Checkov.

Для окончательного завершения анализа необходимо выполнить обновлённый workflow и перенести реальные результаты Syft, Grype, Gitleaks и Checkov в соответствующие разделы этого файла.
